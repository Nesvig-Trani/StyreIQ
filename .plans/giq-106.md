# GIQ-106 — Central Admin cannot disable a unit

## Context

A Central Admin in the City of Raleigh tenant could not disable a unit they created; the modal shows "Failed to disable organization".
Reproduced locally (2026-10-16, dev server :3000, `claude.repro.central`, central_admin tenant 1): `PUT /api/organization/disable/5` → `401 {"error":"Unauthorized"}`.
Root cause: `disableUnit` endpoint (`src/features/units/plugins/endpoints/index.ts:296`) only allows `UserRolesEnum.SuperAdmin`. The sdk (`src/sdk/organization.ts:84`) throws a fixed message and `handleConfirmDisable` (`src/features/units/hooks/useUnitHierarchy.tsx:114`) discards it, so the user never learns why.
The `organization` collection `update` access already allows CentralAdmin within own tenant, and `validateTenantAccess` already enforces tenant scope — only the endpoint role gate is wrong.

Decisions (developer): plan file flat at `.plans/giq-106.md`; block disabling only when the unit has active child units.

## Files to modify

- `src/features/units/plugins/endpoints/index.ts` (`disableUnit`)
  - Allow SuperAdmin and CentralAdmin; other roles → `EndpointError('You do not have permission to disable units.', 403)`; no user → 401.
  - Validate id (`Number.isNaN` → 404) and use `unitId` in the update `where` (currently uses raw `id`).
  - Before update, query active children (`parentOrg equals unitId`, `disabled` false/null, `overrideAccess: true`, `limit: 0`); if any → `EndpointError("Cannot disable this unit while it has active sub-units: <names>. Disable them first.", 409)`.
  - Keep existing tenant check (`validateTenantAccess`) for CentralAdmin.
- `src/sdk/organization.ts` (`disableUnit`): parse the JSON body on failure and throw `new Error(body.error ?? 'Failed to disable unit')`.
- `src/features/units/hooks/useUnitHierarchy.tsx` (`handleConfirmDisable`): `catch (error)` → `toast.error(error instanceof Error ? error.message : 'Failed to disable organization')`.
- Optionally extract the child query into `src/features/units/plugins/queries/unit.queries.ts` (existing home for unit queries) if it keeps the endpoint readable.

No DB migration, no env vars, no new deps. No test runner exists (AGENTS.md), so no new automated tests unless the developer wants a runner added.

## Implementation steps

2. SDK passes through server error message.
3. Hook shows server message in toast, generic fallback.
4. Run `pnpm ci:checks`; commit (conventional: `fix(units): allow central admins to disable units (GIQ-106)`).

## Edge cases and risks

- UI shows the Disable button to every role except Social Media Manager, so Unit Admins will see it and now get a clear 403 message instead of a generic one; hiding it for them is out of scope (note for follow-up).
- Disabled units are filtered out of lists by `disabled` flag only; disabling a unit with users/accounts attached is allowed by decision (not blocked) — users keep `organization_access` rows to a disabled unit. Flag for follow-up if Raleigh expects stricter behaviour.
- `details: error` in the endpoint's 500 branch serialises the raw error; untouched (out of scope).
- Dev DB is shared with real-looking client data: all writes limited to throwaway units; clean up (disable) afterwards, never delete.
- `src/types/payload-types.ts` etc. are already dirty in the main checkout; the worktree is clean — don't copy those changes.

- ✅ Destructive confirmation present — "Disable Unit" modal with Cancel / Disable Anyway and a description of the consequence

- ⚠️ [Low] **copy.consistency** Dialog says "unit" while the toasts say "organization" ("Organization disabled successfully")
- ➖ Loading / empty states of the list — untouched by this change
